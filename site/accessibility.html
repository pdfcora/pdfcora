Accessibility

Documents people can
actually read.

Two halves: the viewer your users touch, and the PDFs your app produces. The first exposes the document’s structure to the platform’s own assistive technology; the second turns an untagged file into one built to PDF/UA-1 — in an app, or unattended on a server, where a backlog is the usual shape of the problem.

The viewer

A page bitmap tells a screen reader nothing. So we expose the structure instead.

The rendered page is hidden from assistive technology, and the document’s own structure is published beside it: headings as headings, lists as lists, figures with their alternate text, table cells, form fields — in reading order.

iOS

VoiceOver

Elements with the right traits and sort priority, so the reading order follows the document rather than the layout.

Android

TalkBack

Compose semantics with a traversal index, so the reading order the document defines is the order TalkBack follows.

Web

Screen readers and keyboard

Real buttons, a visible focus ring, and +, −, Page Up and Page Down while the page has focus. Sized in rem, so the toolbar follows the reader’s text size.

All three

Built to WCAG 2.1 AA

Controls carry names and roles, the page zooms and pages from the keyboard, text scales with the reader’s settings without clipping, and a figure the document leaves undescribed is announced as one rather than skipped in silence.

The documents

Untagged in, PDF/UA out.

  1. Read what is there

    The structure tree, if the document has one, and whether it is tagged at all.

  2. Propose tags

    Rules over the page objects group text into headings, paragraphs, list items, figures and artifacts, in reading order, with a proposed level for each heading.

  3. Describe the figures

    Figures with no alternate text are listed with the page text around them, described on device where the platform can, and written as /Alt — or marked decorative.

  4. Write it into the file

    Accepted proposals become a real structure tree with a parent tree, title, language and an XMP packet declaring PDF/UA-1 — a document any conforming reader understands, not a private annotation layer.

A backlog is the usual shape of the problem

Nobody remediates ten thousand archived PDFs by hand on a phone. The same four steps run unattended: @pdfcora/node for the rules-based proposals, and the Java SDK for the write itself — tagContent takes the blocks in reading order, makes everything else an artifact, and emits the tree, the parent tree, /Lang and the XMP packet. samples/pipeline-java does exactly this, then signs the result. veraPDF passes its output, which is what decides whether the PDF/UA-1 claim is true.

What is missing

The honest list.

  • Tables become paragraphs and vector charts become artifacts, so a chart is not announced.
  • Annotations and form fields are not tagged, so a page with links will not pass PDF/UA after remediation.
  • Reading order is content order. A multi-column page drawn out of order is not reordered — the reviewer sees the numbers and can fix them.
  • No OCR, so a scanned page has no text to tag.
