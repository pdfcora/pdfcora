AI that reads the document,
not your users’ data.

On-device models where the platform has one, your own endpoint where it does not, and nothing at all if you configure neither — the rules-only features still work, which is what makes them useful in a batch job with no user and no model. Every change is a proposal a person accepts, and every accepted change can be undone.

Features

Eight things worth automating.

Grounded answers

Questions answered from the document, with citations to the sentences the answer came from. An answer with no supporting passage is refused rather than invented.

Summaries

A paragraph or key points, for the document or a page range, in a language you name. Long documents are summarised in windows and combined.

Redaction suggestions

Patterns find IBANs, cards, emails, phone numbers, dates, URLs and IP addresses on any device. A model adds names, addresses and ID numbers where one is available.

Smart form filling

Field values proposed from a profile — names, address, contact, IBAN — matched by field name, tooltip and nearby label.

Alt text for figures

Figures in a tagged PDF that lack a description are listed with the page text around them, and described on device where the platform can.

Accessibility remediation

An untagged PDF gets headings, paragraphs, lists, figures and artifacts in reading order, written as a real structure tree. More on accessibility.

Semantic diff

Two revisions aligned sentence by sentence, each change labelled as wording only or a change in meaning, with a one-line summary.

Flat form detection

A printed form with no fields: the lines, boxes and underscores become proposed text fields and checkboxes, labelled from the text beside them.

Where it runs

On device first. Your endpoint second. Rules always.

Each feature asks for a route in order and takes the first answer. Availability is reported per feature and re-read on every call, because a user can turn the platform’s AI off mid-session.

On a server, rules do most of the work

A host has no Apple Intelligence, no AICore and no browser Summarizer, so @pdfiumkit/node reports unavailable for the model routes rather than pretending — and runs the rest unchanged. Redaction suggestions, form proposals, flat form detection and remediation are patterns and rules: no model, no network, no per-document cost. Point a provider at a hosted model when you want the rest. The Java SDK has no AI package yet.

The SDK never downloads a model on its own

It reports available, downloadable, downloading or unavailable with a reason. Downloading is something your app asks for, with prepare(), so a metered connection is never surprised. One reason is worth knowing about: Android’s AICore refuses to run while your app is in the background or the screen is off, which the SDK reports as backgroundUseBlocked.

Review and undo

Nothing is written until someone says yes.

  1. Propose

    Every feature returns items with their page, their text and where they sit, plus a notice your UI must show. Nothing has changed yet.

  2. Show

    The viewer component can draw them as marks over the page with accept and reject, or you can present them your own way.

  3. Apply the accepted ids

    Only what was accepted is written, and an id that was not in the set is an error rather than a silent write.

  4. Undo

    Applying takes a snapshot first, so the document can be reopened exactly as it was.

Privacy

Document text leaves the device only if you send it.

  • On-device routes keep everything local by construction.
  • A custom provider is a small interface you implement — the SDK ships no adapters and calls no vendor. Text reaches an endpoint only because your app configured one.
  • With neither configured, the pattern and rule features still work: redaction suggestions, remediation, flat form detection and form filling all run with no model at all.
  • Alpha prompt APIs stay off unless your app opts in.
