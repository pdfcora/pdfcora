Why PdfiumKit

Stop maintaining three PDF stacks.

Many apps end up with a different PDF library on every platform — and three sets of bugs. PdfiumKit gives you one engine and one API, so a feature behaves the same on an iPhone, an Android tablet and in the browser.

Write it once. Ship it everywhere.

The same types, method names and error cases in Swift, Kotlin and TypeScript — each written the way that language’s developers expect.

Swifttry await page.render(width: 1200)
Kotlinpage.render(width = 1200)
TypeScriptawait page.render({ width: 1200 })

Bad files don’t crash your app.

We pushed all 293 documents from PDFium’s own test corpus through the entire API. Zero crashes. Broken and password-protected files come back as typed errors you can handle.

0crashes

The engine behind Chrome.

Built on PDFium, pinned to a known revision, with the same public API compiled into every platform’s build.

Safe from any thread.

Every document runs on its own serial executor. Call it from anywhere — you can’t corrupt memory by using the wrong thread.

Light enough for mobile.

Recovers when the engine can’t.

A malformed page can stall any PDF engine. On the Web, PdfWorker runs the whole SDK in a Worker behind the same API — so your page stays responsive and a stuck render can simply be terminated.

const doc = await worker.open(bytes)
// same API as in-process
worker.terminate() // page keeps running

Features

Everything your users do with a PDF.

Viewing, searching, marking up and filling in — available today on all three platforms.

  • View & render

    Crisp pages at any size or exact pixel dimensions, with annotations and form widgets on or off.

  • Search text

    Full-text search with result rectangles, text extraction and per-character bounding boxes.

  • Annotate

    Read 15 annotation kinds. Draw ink, add notes and remove annotations — plus highlights on iOS.

  • Fill forms

    Read 8 field kinds and set text, checkboxes and choices — or place native controls right on the page.

  • Navigate

    Outlines, bookmarks and links, so readers can jump straight to what they need.

  • Attachments & metadata

    List and extract embedded files, and read document metadata and permissions.

  • Save changes

    Save in full, or incrementally to keep the original bytes and existing signatures intact.

  • Protected files

    Open password-protected documents, with a clear typed error when a password is needed.

Developer experience

Your first render in four lines.

Async from top to bottom, idiomatic in every language, and nothing to configure before you open a file.

  • async/await on iOS, coroutines on Android, promises on the Web
  • Typed errors instead of native crashes
  • Explicit coordinates — no hidden Y-flip
Swift 
let doc  = try await PdfDocument(url: url)
let page = try await doc.page(0)
let img  = try await page.render(width: 1200)
let hits = try await page.text.search("invoice")
Kotlin 
PdfDocument.open(file).use { doc ->
    val page = doc.page(0)
    val bmp  = page.render(width = 1200)
    val hits = page.text.search("invoice")
}
TypeScript 
const doc  = await PdfDocument.open(bytes)
const page = await doc.page(0)
const img  = await page.render({ width: 1200 })
const hits = await page.text.search('invoice')

Proof, not promises

Tested against the files your users actually send.

Every one of the 293 documents in PDFium’s own test corpus, pushed through the entire public API. Here is exactly what happened.

01

One contract, three SDKs

A single expectations file defines page counts, geometry and failure modes, and all three SDKs are tested against it. Page counts are cross-checked against a second engine, poppler.

02

Pixels in the right place

Rendering is checked by position: a known colour test page must put blue, green and red exactly where the reference engine does — catching bugs that pixel counts miss.

03

Text, verified by hash

Extracted text is checked by exact character count and a SHA-256 of the page text on every platform, so all three independent text decoders must agree byte for byte.

We tell you about the edge cases

One 1,230-byte file stalls PDFium’s renderer. We measured the damage.

It stalls inside the engine, where no cancellation can reach it. So PdfiumKit contains it: every document has its own executor, and with 16 simultaneous stalls on iOS and 10 on Android, other documents kept rendering and the rest of the app kept working. On the Web, PdfWorker recovers completely.

Design decisions

Thread-safe

An actor on iOS, a single-threaded dispatcher on Android, a promise chain on the Web. Misuse raises PdfError.closed instead of corrupting memory.

Typed errors

A closed set of error cases, identical on all three platforms.

Explicit coordinates

PdfRect is always PDF space; toView and toPdf convert in each direction. No hidden Y-flip.

Nothing silently dropped

Every sealed hierarchy has an unknown case, so unmodelled annotation and field types are surfaced, not lost.

Roadmap

What’s coming next.

None of this is available yet — it’s where PdfiumKit is heading, not a promise of dates.

  • In design

    Digital signatures

    Read existing signatures, verify them, and sign documents.

  • In design

    Redaction

    Remove content so it can’t be recovered — text, annotations, form values and metadata.

  • Planned

    Full coverage everywhere

    Highlight, underline and strikeout on Android and Web, and a raw engine escape hatch beyond iOS.

  • Planned

    Accessible viewer

    A viewer designed to conform to EN 301 549 and WCAG 2.1 AA — keyboard navigation, screen readers, reflow.

  • Planned

    Accessibility remediation

    AI-suggested tags, reading order and alt text, always confirmed by a person.

  • Planned

    Bring your own model

    AI features that run locally or on your own endpoint, so documents never leave your infrastructure.
