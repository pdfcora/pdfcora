For engineers

One engine.
Five idiomatic APIs.

PdfiumKit is PDFium, pinned to a known revision, wrapped so that Swift, Kotlin, TypeScript and Java each get the API their developers expect — with the same types, the same method names and the same error cases, on a phone, in a browser and on a server.

Modules

Take the core. Add the rest when you need it.

The core never depends on the AI or UI packages — a build check enforces it — so an app that only renders PDFs ships only the engine. On a server there is no UI to take.

Requirements: iOS 15+ with Swift 5.9 · Android minSdk 23 with all four ABIs · Web and Node as ESM with the .wasm inside the package, Node 18+ · Java 17+ on macOS and Linux, x86-64 and arm64, with the native engine in the jar.

Node is the web package with file and PNG helpers on top, not a second implementation, so anything written against the web SDK runs there unchanged. Java is its own implementation over the native engine: it carries the document API, annotations, form filling, redaction, tagging, signing and the viewer state layer — there is no component to draw, and no AI package yet.

Threading

PDFium is not thread-safe. You never have to care.

iOS

An actor per document

Every call hops onto the document’s actor, so concurrent calls serialise instead of corrupting memory. async/await throughout.

Android

A single-threaded dispatcher

Each document owns one dispatcher; suspending functions run there. Your coroutine scope stays yours.

Web

A promise chain, or a Worker

In-process calls queue behind one chain. PdfWorker runs the whole SDK in a Worker behind the same API, so a stalled render can be terminated without taking the page down.

Node & Java

One thread per document

Node inherits the web SDK’s promise chain. On Java each document owns a thread and every call runs on it, so calling from a request pool is safe — the calls serialise rather than corrupting memory.

Everywhere

A watchdog for the calls that never return

A malformed page can stall inside the engine where no cancellation reaches. Each document has its own executor, and a watchdog marks the engine unresponsive so later calls fail fast with a typed error rather than piling up behind it. A stalled document cannot take the others with it.

Errors

A closed set of errors, identical everywhere.

No native crashes, no untyped throws. The same case names appear in Swift, Kotlin, TypeScript and Java, so error handling ports between platforms unchanged.

Error cases
CaseWhen it happens
passwordRequiredThe document is encrypted and the password was wrong or missing
corruptThe file, or one page of it, cannot be parsed
pageOutOfRangeA page index outside the document
closedThe document was used after close() — raised instead of touching freed memory
invalidOperationThe call cannot apply: tagging a tagged document, a field that is read-only, alt text on a non-figure
unresponsiveThe engine stalled on an earlier call and this document is no longer usable
saveFailed, notLicensedWriting failed, or the feature needs a licence module the key does not carry

Nothing is silently dropped

Every sealed hierarchy — annotation kinds, form field kinds, structure types — has an unknown case carrying the raw value. An annotation PdfiumKit does not model is surfaced, not hidden.

Coordinates

PDF space in, view space out — explicitly.

PdfRect is always PDF space, with the origin bottom-left, normalised so left <= right and bottom <= top. The viewer’s transform() converts in both directions with toView and toPdf. There is no hidden Y-flip anywhere in the API.

TypeScript
Mapping a search hit onto the screen 
const hits = await page.text.search('invoice')
const box  = await page.text.boundingBox(hits[0].start)
const view = viewer.transform().toView(box)  // pixels, origin top-left

Viewer

A viewer you can drop in, or drive yourself.

The state layer — page, zoom, scroll, tool, selection — is a plain value you own, so it transfers between platforms. The UI package renders it; you can also render it yourself and keep only the logic.

Cross-platform state

Zoom, scroll and page travel as data: a session started on a phone resumes in the browser at the same place.

Configurable toolbar

Pick the items and their order, or start from the default and viewing presets. Custom buttons take an icon and an action.

Themeable

Tokens with the same meaning on all three platforms — accent, backgrounds, corner radius, icon size, toolbar height.

Review bar

Marks over the page with accept, reject and apply, used by every AI proposal flow. Nothing is written until someone accepts.

Reference

Every public type, generated from the source.

Each SDK’s reference is produced by that language’s own tool, from the code that ships — so it cannot drift from the API you call. One command builds all five, plus a quickstart page each.

Limits

What it does not do yet.

Kept here rather than in a footnote, because finding out late is worse.

  • The raw PDFium escape hatch exists on iOS only.
  • The Java SDK does not yet read outlines, links or attachments, report page rotation, return search rectangles, or save incrementally except when appending a signature or a structure tree — and it has no licensing module, so unlike the other four it writes unwatermarked output.
  • Java signs as PAdES B-B. A timestamp, which would make it B-T, needs a call to an authority and is not wired up there yet; iOS, Android and the Web take a timestampUrl.
  • Cancelling a render mid-call is not possible on any platform; iOS cancels between progressive steps.
  • Recovering from an engine hang fully is Web-only, through PdfWorker; the other SDKs contain it rather than recover. PdfWorker is re-exported on Node but needs a browser Worker, which Node does not have.
  • Remediation writes tags from rules, not a model: tables become paragraphs, vector charts become artifacts, reading order is content order, and annotations and links are not tagged. The full list is here.
  • There is no OCR, so a scanned page has nothing to tag or search.
  • On an encrypted document, the features that append to the file — signing, tagging, alternate text, creating form fields and incremental saves — are refused, because appended strings would have to be encrypted with the document’s own key. Reading, rendering, filling existing fields, annotating, redacting and saving all work.
